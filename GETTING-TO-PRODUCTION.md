## How to use this document

This runbook is a sequence of **copy-paste prompts**. Each step is sized to be one focused Claude session.

### The session protocol
1. Start a session with the model recommended for the step.
2. **Paste the step's prompt verbatim.** Each prompt already starts with a re-orientation line ("Read this runbook…") so a fresh session picks up context.
3. Let the step finish, including its closeout (it will tick the checklist, append to the Session Log, and update memory).
4. Run `/clear`.
5. Move to the next step.

### Model legend
- 🔴 **Opus 4.8** — correctness-critical, subtle reasoning, concurrency, high-stakes (real money / real locks), or "diagnose this failure." Use Opus even if it costs more; these are the steps where getting it wrong is expensive.
- 🟢 **Sonnet 4.6** — mechanical, well-bounded edits; conversational credential walkthroughs; writing scripts and docs. Fast mode (`/fast`) is fine here.
- 🟢→🔴 escalate — some steps start on Sonnet and say "escalate to Opus if the failure cause is non-obvious." That means: finish the session, `/clear`, and re-run the **same** step's diagnosis on Opus.

You can space these out over days/weeks. Progress survives `/clear` because every step writes to the **Session Log** (bottom of this file) and to project memory.

### Branching rules
Some steps are conversational and **fork** based on your answers or on whether a live test passes:
- **Credential walkthroughs (Phase 2):** Claude asks what you already have; your answers steer it. **Do NOT `/clear` mid-walkthrough.** Stay in the session until that integration's credentials are in `.env`/`config.yaml`.
- **Live test steps:** if the test fails, Claude diagnoses and fixes **in the same session**, then re-runs. Only `/clear` once the step's "done-when" is green.
- `/clear` happens **at step boundaries only.**

### Git & how progress is saved
All work commits **directly to `main`** — no feature branch (solo project, your call). Each fix is an atomic commit (TDD: failing test → code → green, per `CLAUDE.md`).

**Every step ends with the same closeout sequence — this is how progress survives `/clear` and is backed up remotely:**
1. Tick the step's checkbox in this file.
2. Append a dated entry to the Session Log (bottom of this file).
3. Update the `project_golive_runbook_progress.md` memory.
4. `git add -A && git commit` to `main`, then **`git push`** — including the runbook update plus any code/scripts.

Steps that only touch `.env` / `config.yaml` (both gitignored, so secrets never leave the host) still commit & push the **runbook progress update**, so the checklist and Session Log stay current on the remote. Wherever a step's closeout says "commit," read it as **commit to `main` and push.**

### Where things are tracked
- **This file** — master checklist (below) + Session Log (bottom).
- **Memory** — `project_golive_runbook_progress.md` mirrors the checklist so a fresh session recalls state even before reading this file.
